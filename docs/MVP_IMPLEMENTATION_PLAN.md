# 邻里惠首版实施方案

## 1. 本轮目标

在微信小程序 AppID 尚未配置的情况下，先完成一套可在 HBuilderX 中预览、可完整走通核心流程的首版产品：

1. 顾客查看可用购物补贴额度与冻结额度。
2. 顾客查看每一笔福利发放、使用和调整记录。
3. 顾客基于真实订单提交购物补贴申请。
4. 店主为顾客发放福利额度，并对申请进行审核。
5. 顾客查看申请进度和处理结果。
6. 展示清楚、稳定的活动规则与风险边界。

本轮不接微信登录、自动读取外部平台订单、微信零钱转账，也不把演示数据误称为真实云端数据。

## 2. 主要使用者

### 顾客端

主要是中老年熟客。界面必须满足：

- 默认字号偏大，正文不小于 30rpx，关键信息不小于 36rpx。
- 每个页面只突出一个主要动作，避免并排放置多个同权重按钮。
- 不用行业术语，不写“资产、钱包、币、收益、返现”等容易误解的词。
- 金额同时显示数字和用途，状态使用文字解释，不能只依赖颜色。
- 表单即时提示错误，提交前二次确认，提交后明确告知下一步。
- 触控区域不小于 88rpx，减少误触。

### 店主端

主要是妈妈本人。首版管理入口与顾客端放在同一小程序中，使用明显不同的“店主工作台”页面。正式上线前必须接入身份校验，不能仅依赖隐藏入口。

## 3. 信息架构

### 顾客端底部导航

- 首页：可用福利、本期活动、主要操作、最近动态。
- 明细：福利流水和说明。
- 申请：购物补贴申请列表和状态。

### 二级页面

- 申请购物补贴：填写渠道、订单号、实付金额及凭证。
- 活动规则：说明获取、使用、审核、退货处理和禁止事项。
- 店主工作台：汇总待办、发放福利、审核申请。
- 发放福利：选择顾客、金额、原因并确认。
- 审核申请：核对订单、通过或退回并记录原因。

## 4. 核心业务规则

所有金额在代码和数据库中均以“分”为单位存储，展示时再转换为元。

- `账面额度 = 所有已生效福利流水之和`
- `冻结额度 = 所有待审核申请的申请补贴金额之和`
- `可用额度 = 账面额度 - 冻结额度`
- `申请补贴金额 = min(订单实付金额, 当前可用额度)`

提交申请只冻结额度，不直接扣减。审核通过时新增一笔“补贴使用”负向流水；审核退回时释放冻结额度。任何纠错均新增调整流水，不覆盖旧记录。

## 5. 技术方案

### 当前阶段

- 使用 uni-app + Vue 3 Options API，保持 HBuilderX 工程可直接运行。
- 通过 `services/benefit-service.js` 提供统一数据接口。
- AppID 未配置前使用本地持久化演示数据，页面显著显示“演示模式”。
- 在 `uniCloud-alipay/database` 预置正式数据表 Schema，默认禁止客户端直接写入。

### AppID 配置后

1. 接入 `uni-id` 微信登录，得到可信用户身份。
2. 新增云对象承接福利发放、申请提交和审核操作。
3. 云对象检查用户角色、金额上限、幂等键和数据状态。
4. 额度扣减与流水写入使用事务，前端仅展示服务端结果。
5. 管理员身份写入数据库，不在前端代码中硬编码。

## 6. 视觉方向

视觉关键词为“邻里、温暖、可信、从容”。采用米白纸张感背景、深墨绿色正文、橘色提示和大面积留白；避免互联网金融常见的金币、红包雨、上涨箭头和刺激性红色。

品质检查重点：

- 视觉层级：三秒内看懂余额、主操作和规则入口。
- 一致性：卡片圆角、间距、按钮和状态标签保持统一。
- 可读性：强对比、短句、明确单位，不以浅灰小字承载重要信息。
- 状态完整：包含空数据、加载、提交中、成功、错误、冻结和审核退回。
- 安全感：在关键位置解释“免费发放、不能充值、不能转让、不是投资”。

## 7. 本轮验收标准

- 顾客可以完整完成“查看额度 → 提交申请 → 查看待审核状态”。
- 店主可以完整完成“发放福利 → 审核申请 → 查看更新后的记录”。
- 关闭并重新打开小程序后，演示数据仍然存在。
- 重复点击提交不会产生两条记录。
- 订单金额、额度和审核状态的边界均有校验。
- 所有页面在窄屏下不出现横向滚动或被遮挡的主操作。
- 业务页面不出现虚拟币、层级返利、拉人奖励或投资收益表达。
